## Overview
Define a project‑agnostic, OMP‑integrated testing and use‑case generation framework that:

1. **Adapts** to a continuously evolving codebase and architecture.  
2. **Provides** a generic, exhaustive set of use‑case descriptors for each major component of Autonomedia.  
3. **Operates** in three execution modes – *offline* (no code execution), *dry‑run* (simulation, no external side‑effects), and *real* (full end‑to‑end run).  
4. **Ensures** that when Autonomedia runs in testing mode, all posting actions are **paper‑manage** (simulated) and never reach external social‑media APIs.

The framework will be realized as a new OMP skill (`testing-framework`) and associated CLI entry point.

## Functional Requirements

| FR ID | Description | Observable Boundary |
|-------|-------------|----------------------|
| **FR-USECASE_REGISTRY** | Register a declarative use‑case descriptor for any module. | **Schema**: `use_cases/*.yaml` – each file must contain keys `id:string`, `description:string`, `inputs:object`, `outputs:object`. Presence of a valid YAML file is verified by `autonomedia-test validate-usecases`. |
| **FR-ERR_HANDLING** | Provide structured error types for the framework. | **New Module**: `src/testing_framework/errors.py` exposing classes `FrameworkError`, `InvalidModeError`, `UseCaseParseError`. All raised exceptions must subclass `FrameworkError`. |
| **FR-EXTENSIBILITY_HOOK** | Allow downstream projects to register custom validators via a plug‑in entry‑point. | **Filesystem Contract**: Presence of a Python entry‑point module `src/testing_framework/plugins/*.py` with a callable `register(app)`; the framework loads all such modules at start‑up without error. |

## Constraints & Assumptions

- **Assumption**: The host environment has `uv` as the package manager and `playwright` installed – required for any browser‑based sanity checks.  
- **Constraint**: All posting actions in `offline` or `dry-run` mode must be logged to `logs/testing/posting_mock.log` and never result in network traffic (validated via a temporary network block during the run).  
- **Assumption**: Existing OMP logging infrastructure (`src/logger.py`) is available and can be imported.  
- **Constraint**: The framework must be **project‑agnostic** – no hard‑coded references to specific platform APIs (e.g., Mastodon, X). All external integrations are to be added later via the plug‑in hook.  

## Acceptance Criteria (observable)

- **AC‑FR‑TEST_FRAMEWORK_INIT** – Running `autonomedia-test init` creates `~/.autonomedia/testing_state.json` with `initialized:true` and exits with status `0`.  
- **AC‑FR‑USECASE_REGISTRY** – Presence of at least one valid `use_cases/*.yaml` file makes `autonomedia-test validate-usecases` succeed (exit `0`).  
- **AC‑FR‑MODE_EXECUTION** – Executing `autonomedia-test run --mode dry-run` produces a `reports/testing/*.json` file whose schema validates, and no outbound HTTP requests are recorded (can be confirmed with network monitor).  
- **AC‑FR‑PAPER_MANAGE_POSTING** – In `dry-run` mode the file `logs/testing/posting_mock.log` contains simulated payloads; the same command in `real` mode does **not** create this log file.  
- **AC‑FR‑USECASE_GENERATOR** – `autonomedia-test gen-usecases` creates a YAML file for each public module under `src/` with non‑empty `id` and at least one `scenario` entry.  
- **AC‑FR‑ERR_HANDLING** – All framework exceptions inherit from `FrameworkError` and produce a consistent JSON error payload when uncaught.
