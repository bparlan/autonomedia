## Objective

To implement robust AI-driven content rewriting for multi-platform support, fix identified platform handler issues, and enhance platform-specific documentation and UI elements, addressing critical failures found in Milestone 15's implementation. This specification focuses on establishing a functional AI rewriting pipeline and rectifying existing handler bugs and documentation gaps to meet the multi-platform objective of Milestone 15.

---

## Functional Requirements

### AI Rewriting Pipeline Implementation
The system shall implement a functional AI rewriting pipeline that transforms user ideas into platform-specific content drafts.

*   **FR1.1:** The system shall integrate a concrete AI provider (e.g., Gemini, or a specified alternative) for content rewriting. The `RewriteProvider` interface shall be implemented by the chosen AI provider.
*   **FR1.2:** The `src/autonomedia/agents/posting_secretary/worker.py` shall correctly invoke the AI provider's rewrite functionality for content with 'idea' or 'approved' status.
*   **FR1.3:** The AI rewriting process shall generate platform-specific content according to defined constraints (character limits, tone, formatting) for LinkedIn, X (Twitter), and Mastodon.
*   **FR1.4:** The system shall handle empty, malformed, or error responses from the AI provider gracefully, logging the issue and setting the content status to 'failed' with an appropriate error message.
*   **FR1.5:** The system shall correctly transition content status from 'idea' to 'rewriting', then to 'prepared' upon successful AI generation and basic validation, or to 'failed' upon error.
*   **FR1.6:** The `src/web/templates/rewrites.html` UI shall correctly trigger the AI rewriting process via the `/batch-generate` endpoint.
*   **FR1.7:** The `/batch-generate` endpoint in `src/web/app.py` shall correctly invoke the AI rewriting process for approved items and update their status to 'rewriting' or 'prepared'.

### Platform Handler Fixes and Enhancements
The system shall rectify identified issues in existing platform handlers and enhance platform-specific documentation and UI elements.

*   **FR2.1:** **LinkedIn Handler Fixes:**
    *   Correct the typo on line 334 of `src/autonomedia/platforms/linkedin/task_handler.py` from `self.taskHandler_id` to `self.task_id`.
    *   Implement robust session validation and token refresh mechanisms as indicated by TODO comments.
*   **FR2.2:** **X (Twitter) Handler Fixes:**
    *   Add a specific `except` block for rate limit errors (e.g., HTTP 429) in the `post` method to handle retries correctly.
    *   Correct the result appending logic in `batch_post` (lines 303-317) to capture both successful and failed posts accurately.
*   **FR2.3:** **Mastodon Handler Validation:** Ensure the Mastodon handler correctly implements the posting logic as per its current structure.
*   **FR2.4:** **Platform Abstraction Layer:**
    *   Implement the `adapt_content_for_platform` function in `src/autonomedia/core/platform/__init__.py` to perform necessary content adjustments based on platform-specific rules.
    *   Ensure `get_platform_constraints` correctly retrieves and utilizes constraints.
*   **FR2.5:** **Platform Documentation and UI Enhancement:**
    *   Update `src/web/templates/platforms.html` and the `/platform-status` API endpoint in `src/web/app.py` to display detailed platform information, including character limits, tone guidelines, rate limits, and authentication status, as specified in M15S2.
    *   Ensure all platform-specific requirements outlined in `docs/milestones/M15/M15S2.md` and `M15S3.md` are comprehensively documented.

## Non-Functional Requirements

### Performance
*   **NFR1.1:** AI rewriting for a single idea should complete within an acceptable timeframe (e.g., under 60 seconds).
*   **NFR1.2:** Batch posting of multiple tweets (X) should adhere to the specified delays and not exceed total batch processing time limits.
*   **NFR1.3:** Content adaptation and validation should be performed efficiently, within milliseconds.

### Reliability
*   **NFR2.1:** The system must handle AI service failures gracefully, with proper error logging and status updates ('failed').
*   **NFR2.2:** Platform handlers must implement robust retry logic with exponential backoff for transient errors and rate limiting.
*   **NFR2.3:** Session health and authentication must be reliably checked before posting attempts.
*   **NFR2.4:** All errors encountered during AI rewriting, platform posting, or data handling must be logged with sufficient detail for debugging.

### Maintainability
*   **NFR3.1:** Platform handlers must be modular, self-contained, and clearly separated from shared logic.
*   **NFR3.2:** AI rewriting prompts and logic should be easily configurable and modifiable.
*   **NFR3.3:** Anti-detection techniques (delays, viewports, user agents) should be configurable.
*   **NFR3.4:** Platform-specific constraints and limits should be centrally managed and easily updatable.

### Security
*   **NFR4.1:** Authentication tokens and secrets must be stored securely (e.g., environment variables, encrypted vault) and not exposed in logs or error messages.
*   **NFR4.2:** Any new dependencies introduced for AI or platform integrations must be vetted for security.

## Data Flow

1.  **Idea Ingestion:** User submits an idea.
2.  **Approval:** User approves the idea via the web UI.
3.  **Status Update:** Content status changes to 'approved' in the database.
4.  **AI Rewriting Trigger:** The `PostingSecretary` worker picks up 'approved' content.
5.  **AI Content Generation:** The worker invokes the implemented `RewriteProvider` to generate platform-specific content drafts.
6.  **Data Persistence:** Generated content is saved as 'prepared' in the `content` table, associated with specific platforms.
7.  **Status Update:** Content status changes to 'prepared'.
8.  **User Review:** User reviews the prepared content on the "Rewrite" page and potentially makes edits.
9.  **Approval for Posting:** User approves the content via the "Review" page.
10. **Verification & Queueing:** Content status changes to 'ready_to_post', marking it for the posting routine.
11. **Platform Posting:** The `posting_routine` picks up 'ready_to_post' items for each platform, dispatches to the appropriate platform handler, and records the result in `post_history`.

## Constraints

*   **Technology Stack:** Python, FastAPI, Playwright, PostgreSQL, Jinja2.
*   **AI Provider:** Must be a reliable provider capable of generating platform-specific, human-like content within character and tone guidelines. The choice of AI provider needs to be finalized and integrated.
*   **Platform APIs:** Must adhere to LinkedIn, X, and Mastodon API rate limits, authentication flows, and content policies.
*   **Content Adaptation:** Content MUST be adapted differently for each platform; identical cross-posting is prohibited.
*   **Anti-Detection:** All browser interactions must employ anti-detection techniques.

## Assumptions

*   **AI Provider Availability:** A functional AI provider API will be available and accessible.
*   **Platform API Stability:** Platform APIs will remain relatively stable, though monitoring and potential reauthentication mechanisms are required.
*   **Authentication:** Platform tokens can be securely stored and refreshed.
*   **Browser Profiles:** Playwright anti-detection profiles are effective and can be reused across platforms with appropriate configuration.
