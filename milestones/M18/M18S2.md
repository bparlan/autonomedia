## Objective

The evolution of the infrastructure health monitoring introduces a verified health dashboard within the Autonomedia system. The Specification-M18-005 defines the infrastructure data endpoint layer that serves real-time status information to the dashboard developed in SPEC-M18-004. This layer provides the backend data layer that enables the dashboard to display verifiable system status.

## Functional Requirements

### `FR-DASHBOARD_DATA_SOURCE` (Endpoint Contract)

- **Type**: REST API Endpoint Contract
- **Interface Contract**: `/api/health` HTTP GET endpoint accessible at localhost:8000/api/health
- **Expected Behavior**:
  - Returns 200 OK on successful status request
  - Returns JSON object with keys: `database`, `runtime`, `tests`, `src`
  - Each key value is either `"healthy"` or `"unhealthy"`
  - Overall structure validates against `/api/health` JSON schema
- **Observable Boundary**: HTTP 200 response must return valid JSON containing all required health status keys

### `FR-HEALTHCHECK_INTEGRATION` (System Integration)

- **Type**: Backend Configuration Contract
- **Interface Contract**: `healthcheck.py` utility integration
- **Expected Behavior**:
  - `src/autonomedia/checks/healthcheck.py` must implement status collection logic
  - Return function `_get_status_data()` accessible by API endpoint
  - Integration with `/api/health` endpoint must not expose internal implementation details
  - Integration testing with dashboard component must succeed
- **Observable Boundary**:
  - API endpoint must serve JSON that matches the public schema defined in `FR-DASHBOARD_DATA_SOURCE`
  - Web server must not crash during integration
  - Status data must reflect healthcheck utility outputs accurately

## Non-Functional Requirements

### `NFR-PERFORMANCE` (Endpoint Responsiveness)

- **Constraint**: API endpoint must respond to GET `/api/health` requests within 300ms under average load
- **Verification**: Performance test suite must measure end-to-end latency and confirm compliance

### `NFR-SECURITY` (Access Control)

- **Constraint**: `/api/health` endpoint must remain publicly accessible without authentication
- **Verification**: Security audit confirms no credentials required for endpoint access

## Integration Boundaries

The `/api/health` endpoint creates interface boundaries with:

- **Incoming**: HTTP GET requests from frontend `/health` page
- **Outgoing**: Status data aggregation from healthcheck utilities and existing infrastructure services

## Implementation Tasks

1. **Routing Setup**: Create API route registration for `/api/health` endpoint
2. **Health Check Integration**:
   - Add `_get_status_data()` to `healthcheck.py`
   - Implement function to convert raw healthcheck results to status keys
3. **API Endpoint Development**:
   - Implement `/api/health` handler in dedicated API module
   - Return structured JSON response with all required status keys
4. **Schema Validation**:
   - Implement response structure to match defined JSON schema
   - Return 400 Bad Request on validation failure
5. **Integration Testing**:
   - Verify dashboard can fetch and parse `/api/health` response
   - Confirm status indicators update correctly with backend changes
6. **Documentation**:
   - Update API documentation with `/api/health` endpoint details

## Constraints

- The infrastructure data endpoint (`/api/health`) must return valid JSON with all required status keys present.
- The endpoint must not expose internal implementation details of health utilities.
- All integration must comply with existing project architecture patterns.
- No deprecated files (`server.py`) may be referenced or modified.

## Assumptions

- Backend health utilities exist and return valid status information.
- Environment variables and configuration support status data collection.
- Internet connectivity and service discovery are stable for API operations.
- No concurrent access conflicts will occur during status data retrieval.

## Constraints

- **Out-of-Scope Items**:
  - UI styling of `/health` page (handled in prior SPEC-M18-004)
  - Backend server startup configuration (handled by existing infrastructure)
  - Detailed authentication flows (API is publicly accessible per requirements)

## Acceptance Criteria

- Returns 200 OK with valid JSON containing all required keys (`database`, `runtime`, `tests`, `src`)
- All status values are either `"healthy"` or `"unhealthy"`
- Response validates against `/api/health` JSON schema
- Dashboard can successfully fetch and parse the endpoint response
- No server crashes or unhandled exceptions during endpoint access
- Integration with dashboard frontend completes successfully
