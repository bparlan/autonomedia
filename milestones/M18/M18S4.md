#### Objective
Implement the Infrastructure Health Dashboard as a React-based web interface that provides real-time visibility into Autonomedia infrastructure status. This specification addresses critical architectural failures from M18S1 by resolving entry point ambiguity, implementing proper React component integration, and establishing reliable test infrastructure.

##### Milestone Complexity & Multi-Spec Plan
This milestone evolves the infrastructure health monitoring into an integrated, verifiable health dashboard within the Autonomedia system. Building on M18S3's verification framework, this specification focuses on the core implementation challenges:

1. **M18S4**: Infrastructure Dashboard Web Implementation - Resolve entry point ambiguity and React component integration
2. **M18S5**: Dashboard Verification Protocol Optimization - Enhance test infrastructure and validation

The current M18S4 implementation will establish:
- Single active `/health` endpoint serving HTML dashboard
- React component integration with healthcheck.py backend
- Proper test environment setup and execution
- Architecture compliance with established patterns

#### Functional Requirements

##### `FR-DASHBOARD_ENDPOINT`
*   **Type**: Filesystem State Contract
*   **Interface Contract**: `src/web/app.py:72` contains `/health` route handler with React component integration
*   **Expected Behavior**: GET `/health` returns rendered HTML with dashboard UI, includes React component `health.jsx` from CDN, displays four status indicators (database, runtime, tests, src)
*   **Observable Boundary**: HTTP response status 200 with HTML content containing dashboard components, accessible via browser

##### `FR-REACT_COMPONENT_INTEGRATION`
*   **Type**: Structured Schema Contract
*   **Interface Contract**: `src/autonomedia/web/ui/dashboard/health.jsx` exports default component with state management and error handling
*   **Expected Behavior**: React component manages loading/error/success states, fetches `/api/health` endpoint, displays status with "healthy"/"unhealthy" CSS classes, handles null status values gracefully
*   **Observable Boundary**: Component renders without JavaScript errors, responds to API state changes, displays error states visibly

##### `FR-API_ENDPOINT_INTEGRATION`
*   **Type**: Structured Schema Contract
*   **Interface Contract**: `src/autonomedia/web/router.py:35` contains `/api/health` route with `healthcheck.py` integration
*   **Expected Behavior**: GET `/api/health` returns JSON with fields: `database`, `runtime`, `tests`, `src`; each field value is either "healthy" or "unhealthy"; HTTP 200 OK on success, HTTP 500 on unexpected errors
*   **Observable Boundary**: JSON response matches healthcheck.py output exactly, schema validation passes

##### `FR-HEALTHCHECK_UTILITY`
*   **Type**: Filesystem State Contract
*   **Interface Contract**: `src/autonomedia/checks/healthcheck.py` exports `get_health_status()` function
*   **Expected Behavior**: Function returns dictionary with status data for database, runtime, tests, src components; gracefully handles exceptions; returns "healthy" for runtime even when `runtime/sessions` directory missing
*   **Observable Boundary**: Function exists and executes without syntax errors, returns expected JSON-serializable data

##### `FR-TEST_ENVIRONMENT_SETUP`
*   **Type**: CLI Executable Contract
*   **Interface Contract**: `bash tests/M18/test_health_endpoint.sh`
*   **Expected Behavior**: Script tests `/api/health` endpoint returns 200 OK with valid JSON, matches healthcheck.py output, includes required fields with valid status values
*   **Observable Boundary**: Script executes with exit code 0 (all assertions pass) when server running and dependencies available
