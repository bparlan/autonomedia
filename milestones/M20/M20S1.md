#### Objective

Implement automated directory-structure auditing and legacy artifact purge scripts to achieve 100% compliance with the 3-layer architectural pattern. This specification focuses on the first two decomposition items from M20: (1) repository-wide 3-layer pattern audit and compliance verification, and (2) legacy artifact purge and directory cleanup.

The externally observable outcome is a deterministic compliance score of 100% across all Python files, JSON registries, and HTML templates, with all legacy directories (`tests/M18/`, `tests/M16/`) removed or consolidated.

##### Milestone Complexity & Multi-Spec Plan

M20 decomposes into four sequential specifications:

1. **M20S1 (this spec)**: 3-layer pattern audit scripts and legacy artifact purge
2. **M20S2**: Integration binding validation across Core Infrastructure, AI Engine, Platform Adapters, Web Application, and Data Registries
3. **M20S3**: Success criteria verification protocol implementation and automated compliance reporting
4. **M20S4**: Final integration and closure artifact generation

This specification (M20S1) establishes the foundational audit infrastructure and executes the legacy cleanup. M20S2 builds on this to validate cross-layer dependencies. M20S3 wraps the verification into a deterministic protocol. M20S4 produces the final closure artifacts.

#### Functional Requirements

##### `FR-DIR_AUDIT_SCRIPT`
*   **Type**: CLI Executable Contract
*   **Interface Contract**: `uv run python scripts/checks/check_directory_structure.py`
*   **Expected Behavior**: The script walks the entire repository tree, classifies each `.py`, `.json`, and `.html` file by layer, and outputs a JSON compliance report to `storage/data/compliance_report.json`. The report must contain a `compliance_score` (float 0.0–100.0), a `violations` array with file paths and reasons, and a `timestamp` ISO-8601 string.
*   **Observable Boundary**: Exit code `0` when scan completes; JSON report written to `storage/data/compliance_report.json` with valid schema. Exit code `1` if scan fails or report cannot be written.

##### `FR-LEGACY_PURGE`
*   **Type**: CLI Executable Contract
*   **Interface Contract**: `uv run python scripts/checks/verify_legacy_cleanup.py --dry-run` (preview) and `uv run python scripts/checks/verify_legacy_cleanup.py --execute` (apply)
*   **Expected Behavior**: The script identifies legacy directories (`tests/M18/`, `tests/M16/`, `milestones/M17/` if empty, etc.), checks whether their files are referenced by existing code via static import analysis, and either previews changes (`--dry-run`) or executes the purge (`--execute`). Exit code `0` on success; exit code `1` on failure (e.g., referenced files detected).
*   **Observable Boundary**: `storage/data/purge_report.json` written containing `directories_removed`, `files_removed`, and `referenced_files_blocked` arrays.

##### `FR-COMPLIANCE_CHECK`
*   **Type**: CLI Executable Contract
*   **Interface Contract**: `uv run python scripts/checks/validate_3layer_pattern.py`
*   **Expected Behavior**: The script performs static analysis of Python import statements across the repository to verify that layer boundaries are respected. It generates `storage/data/integration_binding_matrix.json` containing `bindings` (array of `{"from": path, "to": path, "valid": bool}`) and `summary.total`, `summary.valid`, `summary.invalid` counts.
*   **Observable Boundary**: Exit code `0` when all bindings valid; exit code `2` when invalid bindings detected; exit code `3` when analysis cannot complete.

##### `FR-SCHEMA_COMPLIANCE`
*   **Type**: Structured Schema Contract
*   **Interface Contract**: All generated JSON report files must conform to the schemas defined in the Schema Contracts section.
*   **Expected Behavior**: Reports written by `check_directory_structure.py`, `verify_legacy_cleanup.py`, and `validate_3layer_pattern.py` must conform to the defined JSON schemas. Invalid schemas trigger a validation error before the script exits.
*   **Observable Boundary**: Schema validation is performed inline; malformed output files are replaced with `{"error": "schema_violation", "details": ...}` and the script exits with code `3`.

#### Non-Functional Requirements

##### `NFR-BACKWARD_COMPAT`
*   **Constraint**: All existing runtime operations (worker, scheduler, AI rewriting, platform posting) must continue to function after the reorganization. No API changes to `src/autonomedia/core/`, `src/autonomedia/ai/`, or `src/autonomedia/platforms/`.
*   **Verification**: `uv run pytest tests/ -q` returns zero failures after reorganization is complete.

##### `NFR-PLATFORM_ISOLATION`
*   **Constraint**: Platform adapters must not share browser profiles or import each other's modules. Each adapter remains isolated under `src/autonomedia/platforms/<platform>/`.
*   **Verification**: Static analysis in `validate_3layer_pattern.py` confirms no cross-adapter imports.

##### `NFR-DETERMINISM`
*   **Constraint**: Audit scripts must produce identical results when run multiple times on the same repository state. Randomness or non-determinism in output invalidates the specification.
*   **Verification**: Running the script twice consecutively produces byte-identical `compliance_report.json` and `integration_binding_matrix.json`.

##### `NFR-AUDIT_TRAIL`
*   **Constraint**: Every reorganization action (file move, deletion) must be logged with timestamp, action type, source path, and destination path to `storage/data/reorg_audit_log.jsonl`.
*   **Verification**: The log file exists and each line is a valid JSON object with required fields.

#### Constraints

*   The scripts must not modify any source code, only produce reports and (optionally) delete legacy directories when explicitly invoked with `--execute`.
*   No changes to existing platform adapter implementations (`mastodon`, `linkedin`, `x`, `facebook_pages`, `threads`, `bluesky`).
*   No changes to AI rewriting engine or core infrastructure APIs.
*   The compliance score must be computed deterministically; non-deterministic results invalidate the specification.
*   Backward compatibility must be preserved; any code change that breaks existing tests is a specification failure.

#### Assumptions

*   The repository root is the working directory when scripts are invoked.
*   Python 3.12+ is available via `uv run python`.
*   All existing tests pass before this specification is implemented (baseline).
*   Legacy directories (`tests/M18/`, `tests/M16/`) are confirmed as migration artifacts with no active dependencies.
*   The `storage/data/` directory exists and is writable; if not, scripts create it.
*   All Python files use standard library `ast` module for import analysis.
